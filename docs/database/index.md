# 索引


## 索引的类型有哪些？

- 按数据结构

| 类型 | 说明 |
|------|------|
| B+ 树 | MySQL 默认，叶子存数据 + 链表，等值/范围/排序都支持 |
| B 树 | B+ 树的前身，节点也存数据，MongoDB 使用 |
| Hash | 等值最快，不支持范围查询 |
| 红黑树 | 内存结构（TreeMap），树太高不适合磁盘 |
| 二叉树 | 退化风险大，仅作理解基础 |

- 按物理存储

| 类型 | 说明 |
|------|------|
| **聚簇索引（主键索引）** | 叶子节点存**完整数据行**，一张表只有一个 |
| **二级索引（辅助索引）** | 叶子节点存**索引列 + 主键值**，查询整行需**回表** |

- 按字段特性

| 类型 | 说明 |
|------|------|
| **主键索引** | 唯一 + 非空，组织数据 |
| **唯一索引** | 列值不允许重复，允许 NULL；兼顾约束与查询 |
| **普通索引** | 无约束，仅加速查询 |
| **前缀索引** | 只索引列前 N 个字符（`index(name(10))`），省空间，不能覆盖索引 |
| **全文索引** | 见数据结构分类 |

- 按字段数量

| 类型 | 说明 |
|------|------|
| **单列索引** | 一个字段 |
| **联合索引（复合索引）** | 多字段按字典序排序，遵循**最左前缀原则** |



## 索引的优缺点是什么？

索引以**空间和写性能**换**读性能**，不是越多越好。

### 优点

| 优点 | 说明 |
|------|------|
| 加速查询 | 全表扫描 O(n) → B+ 树 O(log n)，千万数据 3~4 次 IO 定位 |
| 加速排序 | 索引本身有序，`order by` 免额外排序（避免 filesort） |
| 加速分组 | `group by` 可利用索引有序性，避免临时表 |
| 唯一约束 | 唯一索引保证数据不重复，兼具约束与加速 |

### 缺点

| 缺点 | 说明 |
|------|------|
| 占空间 | 每个索引一棵 B+ 树，随数据量线性增长 |
| 拖慢写 | `insert / update / delete` 都要**同步维护所有索引树**（页分裂、平衡调整） |
| 优化器负担 | 索引多了选择成本上升，统计信息偏差时可能**选错索引** |
| 维护成本 | 需要识别冗余索引（idx(a) 可被 idx(a,b) 覆盖）、无用索引 |

### 使用建议

- 字段唯一性太差不适合做索引
- 更新非常频繁不适合做索引
- 不会频繁查询的字段不适合做索引



## 为什么选择 B+ 树作为 InnoDB 的默认索引？

| 结构 | 淘汰原因 |
|------|----------|
| Hash 表 | **不支持范围查询和排序** |
| 二叉搜索树 | 顺序插入退化为链表，高数据量下查询效率低 |
| 红黑树/AVL | 是二叉，树高 = log₂(n)：百万数据约 20 层 = 20 次 IO，磁盘扛不住 |
| B 树 | 多叉解决了树高，但**节点也存数据行**，单页(16KB)放的索引项少 → 扇出小 → 树偏高 |
| **B+ 树** | 见下 |

- 树矮（扇出大）

- 数据全在叶子层，查询性能稳定

- 任何一次查询都要走到叶子节点，IO 次数恒定（B 树数据散布在各层，运气好坏 IO 次数差异大）

- 叶子双向链表，范围查询天然高效



## 联合索引的数据结构是怎样的？

联合索引仍是**一棵 B+ 树**，索引键是多列拼接的复合值，按**字典序**排序：先按第一列排，相同再按第二列。

```
索引 (a, b) 的叶子层：

[a=1,b=1] [a=1,b=5] [a=1,b=9] [a=2,b=3] [a=2,b=7] [a=5,b=2] [a=5,b=6]
 └── a 全局有序 ──────┘
     b 仅在 a 相同的组内有序；跨组看 b 是乱的
```

最左前缀原则（由排序结构决定）：

| 查询条件 | 能否用到 idx(a,b) |
|----------|-------------------|
| a=1 and b=5 | ✅ a、b 都用上 |
| a=1 | ✅ 用 a |
| b=5（无 a） | ❌ b 全局无序，用不上 |
| a>1 and b=5 | ⚠️ a 范围后，b 失效 |
| a=1 order by b | ✅ 组内 b 有序，免排序 |

### 总结

```
联合索引 = 复合键的一棵 B+ 树，先 a 后 b 字典序
最左前缀不是语法规定，是排序结构的必然结果
范围查询右侧列失效
```

面试要点：复合键字典序、为什么最左前缀、范围右侧失效。



## 为什么 InnoDB 推荐自增主键？

InnoDB 数据按主键顺序组织在聚簇索引上，主键的选择直接决定数据的物理布局。

### 原因一：顺序插入，避免页分裂

```
自增主键：永远追加到最后，页写满顺序开新页
[1|2|3|4] → 满了 → 新页 [5|6|7|8] ✅ 页紧凑

无序主键（UUID）：插入位置随机，目标页满时页分裂
[10|300|500|800] 插入 400 → [10|300|400] + [500|800]
❌ 频繁分裂/合并 → 碎片、IO 放大、缓存命中差
```

### 原因二：主键短，二级索引小

- 每个二级索引叶子都**冗余一份主键值**
- 自增 `bigint` 8 字节 vs UUID 36 字节；主键越短 → 所有索引越小 → 树越矮 → IO 越少

### 总结

```
自增 = 顺序追加：无页分裂、缓存热
主键短：二级索引小、树矮
分布式场景（分库分表）用雪花 ID：全局唯一 + 趋势递增
```

面试要点：顺序插入避免页分裂、主键长度对二级索引的放大效应、分库分表用雪花 ID。
