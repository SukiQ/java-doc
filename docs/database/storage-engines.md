# 存储引擎


## InnoDB 和 MyISAM 的区别？

| 对比 | InnoDB | MyISAM |
|------|--------|--------|
| 事务 | ✅ 支持（ACID） | ❌ 不支持 |
| 崩溃恢复 | ✅ redo log 自动恢复 | ❌ 崩溃易损坏，需 repair |
| 锁粒度 | **行级锁** | 只有**表锁** |
| 外键 | ✅ | ❌ |
| 索引结构 | **聚簇索引**（叶子存整行） | 非聚簇（叶子存数据地址指针） |
| MVCC | ✅ | ❌ |
| count(*) 无 where | 每次扫（MVCC 下不同时刻行数不同） | **存了总行数，O(1)** |
| 全文索引 | 5.6+ 支持 | 支持 |
| 哈希索引 | ❌（自适应哈希自动） | ❌ |

### 为什么 5.5+ 默认 InnoDB

- 互联网场景必须**事务 + 并发写**：MyISAM 表锁意味着任意写都阻塞整表读写
- 崩溃安全：MyISAM 崩溃后表损坏是常态，InnoDB 靠 redo 恢复
- MyISAM 仅剩优势：表级只读统计、无事务的日志表（现在也基本被 InnoDB 覆盖）

### MyISAM 的历史地位

- 5.5 前默认引擎；现在基本弃用
- 了解它主要为了回答"为什么 InnoDB 是聚簇索引、MyISAM 不是"：MyISAM 索引与数据分离，二级索引与主索引结构相同（都存地址）

### 总结

```
InnoDB：事务 + 行锁 + 聚簇 + 崩溃恢复，互联网标配
MyISAM：表锁、非聚簇、count 快，已淘汰
8.0 已彻底移除 MyISAM 作为系统表引擎
```

面试要点：事务/锁粒度/聚簇三大区别、count(*) 行为差异的原因（MVCC 行数不定）、MyISAM 索引存地址 vs InnoDB 二级索引存主键。



## Buffer Pool 是什么？

InnoDB 的**内存缓存池**：以页（16KB）为单位缓存磁盘数据，读写都先走内存，是 MySQL 性能的核心。

### 结构

```
Buffer Pool（内存）
├── 数据页（缓存表数据/索引）
├── 索引页
├── change buffer（写缓冲）
├── 自适应哈希（AHI）
└── 锁信息、数据字典
```

- `innodb_buffer_pool_size`：通常设为物理内存的 60%~70%
- 命中率 = read_requests / (read_requests + reads)，应 > 99%

### 改进版 LRU（young / old 两区）

朴素 LRU 的问题：**一次全表扫描会把整个缓存刷掉**（污染），之后热点数据全部 miss。

```
LRU 链表：
[ young 区（热数据，5/8）][ old 区（冷数据，3/8）]
                              ↑ 新页先进 old 区头部

新读取的页 → 先放 old 区头部
old 区停留超过 innodb_old_blocks_time（默认 1 秒）再次被访问 → 晋升 young 区
（全表扫描的页在 1 秒内只被读一次，很快被淘汰，不会污染 young 区）
young 区前 1/4 以内被访问 → 不移动（避免热页抖动）
```

### change buffer（写缓冲）

- 写**非唯一二级索引**页不在缓存时：先记到 change buffer，**不等读盘**
- 后续该页被读入时合并（merge），或后台定期合并
- 省去大量随机读 IO，适合写多读少表；唯一索引要校验唯一性必须读页，**用不上**

### 脏页与刷盘

```
页被修改 → 成为脏页（与磁盘不一致）→ 由后台线程择机刷盘
触发刷盘：redo log 写满（推 check point，主动"抖一下"）/ 内存不足淘汰 / 正常关库
```

redo 写满是抖动主因：合理设置 redo 大小（`innodb_log_file_size`）减少强制刷脏。

### 总结

```
Buffer Pool：以 16KB 页缓存数据，命中率是第一指标
LRU 改进：young/old 分区 + 停留时间门槛，防全表扫描污染
change buffer：二级非唯一索引的写缓冲，写多读少受益
脏页：redo 写满会强制刷盘 → 业务抖动
```

面试要点：朴素 LRU 的污染问题与两区方案、old 区晋升条件（innodb_old_blocks_time）、change buffer 为什么唯一索引用不上、脏页刷盘的触发点。
