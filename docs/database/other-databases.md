# 其他数据库


## 不同类型的数据库有什么区别？

| 类型 | 代表 | 数据模型 | 强项 | 典型用途 |
|------|------|----------|------|----------|
| 关系型 | MySQL / PostgreSQL | 二维表 + SQL | 强一致 ACID、复杂查询、生态成熟 | 业务主数据 |
| 键值 | Redis | KV 内存结构 | 极高读写速度（10 万+ QPS） | 缓存、分布式锁、排行榜 |
| 文档 | MongoDB | BSON（类 JSON） | schema 自由、嵌套结构免 JOIN | 弹性结构数据、高写入吞吐 |
| 搜索引擎 | Elasticsearch | 倒排索引 | 全文检索、多维聚合、近实时 | 站内搜索、日志分析（ELK） |
| 列式分析 | ClickHouse | 列式存储 | 大宽表聚合极快（亿级秒回） | OLAP 报表、行为分析 |
| 时序 | InfluxDB / Prometheus | 时间线 | 按时间写入查询、高压缩 | 监控指标、IoT |



## PostgreSQL：另一个关系型

与 MySQL 同为开源关系型，走"功能丰富、标准严谨"路线；复杂查询、类型系统与扩展生态强于 MySQL。

### 与 MySQL 的对比

| 对比 | PostgreSQL | MySQL（InnoDB） |
|------|------------|-----------------|
| MVCC | 旧版本留在表内（多版本元组），VACUUM 清理 | undo log 版本链 |
| 串行化 | **SSI**（可串行化快照隔离），无幻读 | gap lock / next-key lock 防幻读 |
| 复杂 SQL | 优化器强，CTE / 窗口函数 / 物化视图早已有 | 8.0 才补齐窗口函数、CTE |
| 数据类型 | 数组、**JSONB**（可索引）、范围类型、自定义类型 | 类型系统简单，JSON 能力弱 |
| 索引 | B-tree / Hash / **GIN** / GiST / BRIN / 部分索引 / 表达式索引 | 以 B-tree 为主 |
| GIS | **PostGIS** 事实标准 | 空间能力有限 |
| 复制 | 物理流复制 + 逻辑复制 | binlog 主从 |
| 连接模型 | 每连接一个**进程**，高并发需 PgBouncer 连接池 | 每连接一个线程 |
| 国内生态 | 相对小众 | 绝对主流：中间件、云服务、人才 |

### 独特优势

- **JSONB**：二进制 JSON，可建 GIN 索引、可查询——关系库里嵌"文档模型"
- 扩展生态：PostGIS（GIS）、TimescaleDB（时序）、**pgvector**（向量检索）、Citus（分布式）
- 很多国产/云数据库以 PG 为底座：openGauss、PolarDB-PG、Supabase

### 什么时候选

- GIS、复杂分析 SQL、JSONB 半结构化、向量检索 / 时序扩展需求 → PG
- 常规业务 CRUD，要生态与运维省心 → MySQL



## Redis：内存键值

数据全在内存，微秒级响应；五大结构 + 特殊结构、持久化、主从/哨兵/集群，定位**缓存与高速读写**，典型场景：缓存、分布式锁、计数限流、排行榜、消息队列。

不适用：大 value（拆分）、当持久化主存储用（内存贵、可能丢数据）——数据真相仍在 MySQL。

已拆分为独立章节：[Redis 基础与数据结构](/redis/basic)、[持久化与内存](/redis/persistence)、[主从与集群](/redis/high-availability)、[缓存与分布式锁](/redis/cache)。



## MongoDB：文档数据库

BSON（类 JSON）存储，一条文档存整个对象/嵌套数组，**无需 JOIN 拆表**。

### 核心能力

| 能力 | 说明 |
|------|------|
| Schema 自由 | 同集合文档结构可不同，字段增删无需 DDL，适合需求多变 |
| 水平扩展 | 原生分片（Sharding），按 shard key 自动分散 |
| 高可用 | 副本集（Replica Set）：一主多从，自动选主 |
| 查询能力 | 丰富查询 + 二级索引 + 聚合管道 + 地理空间索引 |
| 事务 | 4.0+ 支持多文档 ACID，但性能与能力弱于关系库 |

### 典型场景

| 场景 | 理由 |
|------|------|
| 弹性结构数据：内容管理、商品属性（不同品类字段不同） | schema 自由，新增字段零成本 |
| 高写入吞吐：日志、埋点、IoT | 写性能好，分片易扩 |
| 地理位置：附近的人/门店 | 原生 2dsphere 索引 |
| 嵌套结构：Feed 流、评论树 | 一次读出，免 JOIN |

### 不适用

- 强一致性多表事务（转账类）→ MySQL
- 复杂多表关联分析 → ClickHouse
- 纯 KV 缓存 → Redis 更轻



## Elasticsearch：搜索引擎

基于 Lucene 的分布式搜索分析引擎，写入后近实时（NRT，约 1s）可查。

### 核心能力

| 能力 | 说明 |
|------|------|
| 倒排索引 | 分词 → 词项 → 文档列表，按"内容"反查"文档"，全文检索的基础 |
| 分布式 | 索引分 shard，每 shard 多副本；自动路由与负载均衡 |
| 聚合分析 | 分组、统计、指标多维聚合，日志分析（ELK）主力 |
| 近实时 | 写入 → refresh（1s）→ 可搜索，不是实时 |

与 MySQL 的粗略类比：index ≈ 表，document ≈ 行；但**无事务、不适合频繁更新**（每次更新要重建倒排）。

### 典型场景

站内搜索（商品/订单/内容）、日志采集分析（ELK/EFK）、多维聚合报表

### 不适用

- 强一致事务 → MySQL
- 精确 KV 点查 → Redis
- 深分页（from + size 深翻页代价大，用 search_after）



## ClickHouse：列式分析

真正的列式 OLAP 数据库，单表聚合亿级数据秒级返回。

### 核心能力

| 能力 | 说明 |
|------|------|
| 列存 + 压缩 | 只读涉及的列，同列数据类型一致、压缩率高，IO 极小 |
| 向量化执行 | 按批按列计算，充分用 CPU SIMD |
| MergeTree 引擎 | 主键排序存储、分区裁剪、后台合并 |
| 写入模式 | append-only + 批量写性能极好；单条写/update/delete 弱 |

### 典型场景

用户行为分析、运营报表、日志分析、监控指标聚合

### 不适用

- OLTP：点查、高频更新、事务 → MySQL
- 复杂 JOIN（大宽表 + 物化视图思路替代）

---

时序数据库（InfluxDB、Prometheus）面向监控/IoT 的"按时间写、按时间读"，领域专用，一般作为监控栈组件出现，不再展开。

实际架构中它们通常**各司其职、协同工作**：

```
MySQL（业务事实）
  ├─ Redis      缓存热点，扛读流量
  ├─ MongoDB    存弹性结构 / 高写入数据
  ├─ ES         同步一份做搜索 / 日志
  └─ ClickHouse 订阅 binlog 做分析
```
