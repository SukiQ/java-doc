# Redis 持久化与内存


## RDB 和 AOF 的区别？

| 对比 | RDB 快照 | AOF 日志 |
|------|----------|----------|
| 原理 | 某时刻全量内存快照（二进制） | 每条写命令追加到日志 |
| 触发 | `save`（阻塞）/ `bgsave`（fork 子进程）/ 自动条件 | 每次写入后（按 fsync 策略） |
| 数据安全 | 两次快照之间的数据会丢 | 最多丢 1s（everysec） |
| 文件与恢复 | 文件小、恢复快 | 文件大、恢复慢（逐条重放） |
| 性能影响 | fork 瞬间开销 | everysec 后台线程刷盘 |

### AOF 三种刷盘策略

| appendfsync | 说明 |
|-------------|------|
| always | 每条命令刷盘，最多丢一条，最慢 |
| **everysec（默认）** | 每秒刷盘，最多丢 1 秒，折中 |
| no | 交给 OS，最快，丢多少看运气 |

### AOF 重写

日志越来越大 → `bgrewriteaof` fork 子进程，按**当前内存数据**生成等价最小命令集（100 次 incr 重写为 1 条 set），期间新写命令同时写入重写缓冲区，最后追加。

### 混合持久化（4.0+，5.0 默认）

重写时：RDB 格式头部（全量）+ AOF 增量尾部。恢复快 + 丢失少，生产推荐。

```ini
aof-use-rdb-preamble yes
```

## bgsave 期间还能写入吗？

能。fork 后父子进程**共享物理内存页**，子进程读旧页生成 RDB；父进程修改某页时触发**写时复制（COW）**，复制该页再写。

注意两个坑：

- fork 本身会瞬间阻塞（复制页表），大内存实例明显
- 写入密集时 COW 复制大量页，内存可能翻倍 → 预留内存 / 降低 COW 概率

## 过期 key 是怎么删除的？

惰性 + 定期双管齐下：

| 策略 | 做法 |
|------|------|
| **惰性删除** | 访问 key 时检查过期才删；不访问就一直占内存 |
| **定期删除** | 每 100ms（`hz=10`）随机抽 20 个带 TTL 的 key，删除其中过期的；过期占比 > 25% 就再抽一轮 |

- 主从复制：**从库不主动删**，等主库删除后同步 DEL 命令（保证一致性）
- 惰性 + 定期漏掉的，交给内存淘汰策略兜底

## 内存满了怎么办？（淘汰策略）

`maxmemory` 达到上限后按 `maxmemory-policy` 淘汰（8 种）：

| 策略 | 范围 | 规则 |
|------|------|------|
| **noeviction（默认）** | — | 拒绝写入，返回 OOM 错误 |
| **allkeys-lru** | 全部 key | 近似 LRU，最常用的缓存策略 |
| **allkeys-lfu**（4.0+） | 全部 key | 按访问频率，热点更准 |
| allkeys-random | 全部 key | 随机 |
| volatile-lru / lfu / random | 有 TTL 的 key | 同上，只淘汰会过期的 |
| volatile-ttl | 有 TTL 的 key | 剩余存活时间短的先走 |

- 近似 LRU：随机采样 `maxmemory-samples`（默认 5）个 key 淘汰最久未用的，省去全量链表
- LFU：对数计数器 + 随时间衰减，避免"历史热点"赖着不走
- 缓存场景推荐 `allkeys-lru` / `allkeys-lfu`；若混存不可丢数据则 noeviction + 容量规划

## 大 key 与热 key 问题？

**大 key**（参考阈值：String > 10KB，集合 > 5000 元素）：

- 危害：内存不均、操作慢查询、删除/序列化阻塞、网卡打满
- 排查：`redis-cli --bigkeys`、RDB 离线分析
- 治理：拆分（大 Hash 分桶）、压缩、删除用 `UNLINK`

**热 key**（单 key QPS 极高，如爆款商品）：

- 危害：单分片 CPU/带宽打满
- 治理：本地缓存兜一层、key 加后缀打散多副本随机读、读写分离
