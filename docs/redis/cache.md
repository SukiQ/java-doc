# Redis 缓存与分布式锁


## 缓存穿透、击穿、雪崩的区别？

| 问题 | 定义 | 典型场景 |
|------|------|----------|
| **穿透** | 查询**不存在**的 key，缓存和 DB 都没有 | 恶意伪造 id 刷接口 |
| **击穿** | **热点 key 过期瞬间**，大量并发直击 DB | 秒杀商品缓存到期 |
| **雪崩** | **大量 key 同时过期**或 **Redis 整体宕机** | 凌晨批量预热的缓存同一时刻到期 |

三者都是"请求绕过缓存打到 DB"，区别在范围与成因。

### 解决方案

| 问题 | 手段 |
|------|------|
| 穿透 | 缓存空值（短 TTL，如 60s）；**布隆过滤器**前置拦截；参数合法性校验、限流 |
| 击穿 | **互斥锁重建**：setnx 抢锁，仅一个请求回源，其余等待/返回旧值；**逻辑过期**：不设 TTL，value 里带过期时间，过期后异步重建；热点 key 永不过期 |
| 雪崩 | 过期时间加随机值打散；Redis 高可用（哨兵/集群）；多级缓存（本地 + Redis）；限流降级兜底 |

布隆过滤器：说"不存在"一定不存在，说"存在"可能误判；不支持删除（计数布隆变体除外）。

## 缓存与数据库的一致性怎么保证？

主流方案：**Cache Aside——读：先读缓存，未命中读 DB 回填；写：先更新 DB，再删除缓存**。

### 为什么是"更新库 + 删缓存"

| 疑问 | 答案 |
|------|------|
| 为什么删缓存而不是更新缓存？ | 并发写时更新顺序不确定会留下脏数据；懒加载按需回填更简单 |
| 为什么不能先删缓存再更新库？ | 删后另一个读请求把**旧值**回填进缓存，之后一直脏 |
| 为什么不能只更新库不删缓存？ | 缓存里的旧值要等到自然过期才失效 |

### 残余不一致与对策

- **删除失败**：删除动作进入 MQ 重试；或 canal 订阅 binlog 删缓存（业务零侵入）
- **读写并发的极小窗口**（读请求未命中后读到了旧值回填）：延迟双删——更新库后 sleep 几百 ms 再删一次
- 强一致需要"读写都加锁"，代价大；**一般接受最终一致**，窗口通常毫秒级

## 分布式锁怎么实现？

### 演进过程

```java
// 1. setnx + expire 两条命令：加锁后宕机 → 死锁
jedis.setnx("lock", "1");
jedis.expire("lock", 10);

// 2. 一条原子命令解决（NX + EX）
jedis.set("lock", uuid, SetParams.setParams().nx().ex(10));

// 3. 误删别人的锁：自己的锁过期后被别人持有，删除时校验 value
//    校验 + 删除必须原子 → Lua 脚本
if (redis.call('get', KEYS[1]) == ARGV[1]) then
    return redis.call('del', KEYS[1])
else return 0 end

// 4. 业务没执行完锁过期 → 看门狗自动续期（Redisson）
```

### Redisson

| 能力 | 实现 |
|------|------|
| 可重入 | hash 结构：field 存线程标识，value 存重入次数 |
| 看门狗 | 默认锁 30s，每 10s（1/3）检查持有则续期；**不传 leaseTime 才生效** |
| 原子性 | 加锁/解锁全部 Lua 脚本 |
| 公平锁/读写锁/信号量 | 同 JVM 语义的分布式版 |

### 主从切换丢锁与 RedLock

主库加锁成功、还没同步给从库就宕机，新主上没有这把锁 → 两个客户端同时持锁。

**RedLock**：向 N 个（如 5 个）**独立**主库依次加锁，多数派成功且总耗时小于锁有效期才算成功。

争议（Martin Kleppmann vs antirez）：时钟跳变/进程暂停可能破坏安全性；运维 5 个独立实例成本高。**实践中：绝大多数场景单实例 Redisson + 看门狗已足够，要求更高用 ZooKeeper/etcd（CP，性能低）。**
